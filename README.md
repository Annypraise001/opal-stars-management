# Opal Stars Management

## Run locally

Use Node.js 20 or newer. From this directory:

```powershell
npm install
Copy-Item .env.example .env
```

Set `SESSION_SECRET` in `.env` to a unique random value of at least 32 characters, then start the app:

```powershell
npm run dev
```

Open `http://localhost:3000`. SQLite creates `data/opal.sqlite` automatically. That directory is excluded from Git and blocked from static web access.

## API

- `GET /api/health`
- `GET /api/celebrities?page=1&perPage=12&search=...`
- `GET /api/payment-config`
- `POST /api/bookings` (multipart form data; proof file required only when a configured payment method is selected)
- `POST /api/auth/register`
- `POST /api/auth/login`
- `GET /api/auth/me`
- `POST /api/auth/logout`
- `POST /api/newsletter`
- `POST /api/inquiries`

Registration passwords are stored as scrypt hashes. Login sessions use random opaque tokens stored as hashes in SQLite and sent in HttpOnly, SameSite cookies. Auth routes are rate-limited; mutating API routes validate the request origin when a browser sends one.

Newsletter subscriptions and booking, fan-card, donation-interest, and contact inquiries are persisted locally. Donation checkout submissions with payment proof are saved as pending review; manual payment is not processor-verified. Email delivery is not configured.

The `/book` page shows the 29-entry sample catalog used to reproduce the provided design reference. Confirm the approved talent roster, booking availability, prices, portraits, and image usage rights before using those sample records publicly.

## Booking and payment setup

The `/booking?celebrity=<catalog-id>` page provides Event Details, Requirements, and Payment steps. Booking requests can be submitted without email or payment configuration. Payment methods are only listed when their real receiving details and `BOOKING_SERVICE_FEE_PERCENT` are configured. With no payment configuration, no QR or bank details are displayed and visitors may submit a booking request without payment.

Set these payment keys in the local `.env` or deployment environment. The `.env` file is ignored by Git and is the single source used by both booking and donation checkout:

- Set `BOOKING_SERVICE_FEE_PERCENT` to your approved numeric percentage.
- Set the enabled wallet addresses with `BITCOIN_ADDRESS`, `ETHEREUM_ADDRESS`, and `USDT_ADDRESS`. QR codes are generated from each wallet address; USDT is labeled BEP20 / BNB Smart Chain.
- For Bank Transfer, configure `BANK_NAME`, `BANK_ACCOUNT_NAME`, `BANK_ACCOUNT_NUMBER`, `BANK_ROUTING_OR_SORT_CODE`, `BANK_SWIFT_BIC`, and `BANK_REFERENCE_INSTRUCTIONS`. Optional fields include `BANK_BRANCH_CODE`, `BANK_ADDRESS`, and `BANK_IBAN`.
- Set `PAYMENT_PROOF_DIRECTORY` to persistent private storage in production. Uploaded proof is limited to 10 MB, validated by file signature, and not served publicly.

The Bitcoin QR image provided in chat was not available as a workspace file, so the app currently generates a clean QR from `BITCOIN_ADDRESS`. To use a supplied image later, place it at `public/images/qr/bitcoin-qr.jpg` and update the payment QR renderer in `booking.js` and `donate.js`. Payment details are changed in `.env`; restarting the server reloads them. Selecting a configured method and uploading proof records a pending-review booking or donation; it does not confirm settlement.

Run the API integration tests with `npm test`.

## Deploy publicly

The included `render.yaml` defines a Render web service and a persistent 1 GB disk for SQLite. The production session secret is generated by Render, and `/api/health` is used as the health check. The starter service and persistent disk require a paid Render plan.

1. Create a GitHub repository and push this `starline` project to it. Do not commit `.env` or `data/`.
2. In Render, choose **New +** then **Blueprint**, and connect the GitHub repository containing `render.yaml`.
3. Review the service and disk costs, then create the Blueprint. Render will build and publish the site and show its public `onrender.com` URL.
4. Open that URL and test account registration and an inquiry. Use the Render dashboard to add a custom domain and configure its DNS if desired.

The website can be public as soon as the Render service is deployed. Search engines may take time to index it; a verified custom domain and sitemap are recommended before actively promoting it. Payment processing and outbound email still require their own provider accounts and credentials.
